# ImaginAI - システム仕様

## 1. システム概要

ImaginAIは、AI画像・動画・音楽・音声生成APIを専用GUIで操作するデスクトップアプリケーションである。Electronで構築され、複数のAPIプロバイダを並列にサポートする:

- **Google AI Studio** (内部識別子: `gemini`): Gemini Nano Banana 系 (画像) / Veo 3.1・Gemini Omni Flash (動画) / Lyria (音楽) / Gemini TTS (音声)。`@google/genai` SDK 経由で呼び出す。
- **OpenAI** (内部識別子: `openai`): GPT Image 2.5 (Flare / Sunburst) (画像)。`openai` SDK 経由で呼び出す。

両プロバイダはデータスキーマ・UI 構造ともに完全に対称な形で扱われる。コード内識別子は `gemini` / `openai` で統一し、ユーザー向け表示文字列のみ「Google AI Studio」「OpenAI」を使う二層構造で運用する。

## 2. アーキテクチャ

### 2.1 プロセスモデル

- **Mainプロセス**: IPC通信、ファイルI/O、API呼び出し、設定管理、APIキー暗号化、ウィンドウ管理を担当する。
- **Preloadプロセス**: `contextBridge`を通じてMainプロセスとRendererプロセスを安全に橋渡しする。
- **Rendererプロセス**: React + MUI によるUIを担当する。

## 3. 機能仕様

### 3.1 画像生成

- ユーザーはモデルを選択し、パラメータ（アスペクト比、解像度、生成枚数）を設定し、プロンプトを入力し、任意で参照画像を添付する。
- パラメータはモデルの対応状況に基づいて検証される（例: 21:9は対応モデルのみ、4Kは対応モデルのみ）。モデルが画像入力非対応の場合は参照画像UIが非表示、ネガティブプロンプト非対応の場合はネガティブプロンプト欄が非表示、生成枚数が1枚のみのモデルでは枚数スライダーが非表示となる。
- 出力フォーマットは Gemini では PNG（API の既定値。`response_format.mime_type` は指定しない）、OpenAI では PNG / JPEG / WebP から選択できる。セーフティフィルターはどちらも API 側で制御されており、ユーザー選択不可。
- 参照画像はファイル選択、ドラッグ＆ドロップ、または履歴エントリから追加できる。サムネイルとして表示され、個別に削除可能。
- 「生成」ボタンでAPIリクエストを送信する。生成中はボタンが無効化され、ローディングインジケータが表示される。
- 成功時は結果が自動的に履歴に保存される。失敗時のメッセージは2層構造で扱う:
  - **インフラ系エラー**（HTTP 4xx/5xx、gRPCステータス、ネットワーク等）: ユーザー向けに行動指針付きで言い換えたローカライズ文言を表示。
  - **コンテンツ系ソフト失敗**（HTTP 200だが生成物0件: Safetyブロック、Recitation、モデル拒否等）: 「{種別}が生成されませんでした。詳細を確認してください。」のみ事実として表示する（プロンプト変更を促す不確かなアドバイスは出さない）。
- 「詳細」リンクをクリックすると、APIから返された診断情報（`finishReason`、`promptFeedback.blockReason`、`safetyRatings`、テキストパートに含まれる拒否理由、Veoの`raiMediaFilteredReasons`等）を生で確認できる。
- ネットワークエラー発生時はリトライボタンを表示し、ユーザーがリトライ可否を選択できる。
- 生成前に履歴保存先のディスク空き容量を確認し、100MB未満の場合は警告を表示する。
- 履歴件数が設定された上限（10,000件）を超えている場合、生成がブロックされる。

### 3.2 履歴管理

- 各生成結果はメタデータ（JSON）と生成ファイル（画像/動画/音楽）として保存される。
- 履歴はサムネイルグリッドでフレックスレイアウト表示され、更新日降順でソートされる。ページネーション（50件ずつ）によるインフィニティスクロール（遅延ロード）で表示される。
- 左クリックでモードレスビューアウィンドウに画像を表示する（動画の場合は動画ビューアで再生、音楽の場合は音楽プレイヤーで再生）。複数枚生成の場合、すべてをそれぞれ別ウィンドウで開く。
- 右クリックでコンテキストメニューを表示: プロンプトに追加、名前をつけて保存（複数枚の場合は各画像のダイアログを順次表示）、パラメータ復元、削除。
- ヘッダーメニュー: すべて削除、すべて圧縮保存して削除（ZIPエクスポート、圧縮中はプログレスバーを表示）。
- 各エントリには生成所要時間（API呼び出し開始から完了まで）が記録され、履歴カードに表示される。
- 履歴パネルの高さは上辺のドラッグで調整可能。
- プロンプトテキストによる部分一致検索でフィルタリング可能。

### 3.3 動画生成

動画モデルは提供 API が2系統ある。どちらを使うかはモデル定義の `gemini.videoApi` フィールドで宣言する（省略 = Veo の predictLongRunning 経路、`'interactions'` = Interactions API 経路）。

#### Veo 3.1 系

- Veo 3.1モデル（Lite/Fast/Standard）による動画生成に対応する。
- パラメータ: 長さ（4/6/8秒）、動画解像度（Lite は 720p/1080p、Fast と Standard は 720p/1080p/4k）、アスペクト比（16:9/9:16のみ）、ネガティブプロンプト。
- 添付画像の使い方は2通りあり、参照画像エリアのトグル（`gemini.videoReferenceMode`）で切り替える。
  - **開始フレーム**（`firstFrame`・既定）: 1枚だけを `image` として送り、その画像から動き出す（Image-to-Video）。全 Veo モデルで利用可能。
  - **被写体参照**（`reference`）: 最大3枚を `config.referenceImages`（`referenceType: 'asset'`）として送り、被写体の見た目を保ったまま生成する。`gemini.maxSubjectReferenceImages` を宣言しているモデル（Veo 3.1 / Veo 3.1 Fast）のみ。ai.google.dev のパラメータ表では Veo 3.1 Lite は `referenceImages` が n/a とされているため、Lite は宣言しない。
  - 被写体参照を使う場合、API 仕様上 **長さは8秒固定**。生成ボタンで検証し、サービス側でも防御的に 8 に固定する。
  - モード切替時は、新しいモードの上限を超える添付画像を破棄する。上限の算出は `resolveMaxReferenceImages()`（編集モードは常に1枚）に集約している。
- Veoモデル選択時は画像固有のUI（出力解像度）が非表示となり、動画固有のUI（長さ、動画解像度）が表示される。シード値は UI に無い（`@google/genai` の Developer API モードが `seed` を拒否するため、リクエストにも含めない。レスポンスが返した場合のみ履歴に記録する）。
- 動画生成はVeo APIの非同期ポーリング（Long-Running Operation）方式で行われ、生成中は経過時間が表示される。ポーリング間隔: 10秒。
- 生成された動画はMP4形式で履歴ディレクトリに保存される。
- サムネイルはffmpegにより1秒目のフレームから抽出される。ffmpegが利用不可の場合はサムネイルなし。
- 1080p/4K解像度の場合、長さは8秒のみ指定可能（生成ボタンで検証）。
- 参照画像を添付することで画像→動画生成（Image-to-Video）または被写体参照生成が可能（上記トグルで選択）。
- 音声はモデルにより自動的に生成される（ユーザー制御不可）。
- 人物生成の制御はモードに応じてAPIが自動的に適用する（ユーザー制御不可）。

#### Gemini Omni Flash（`gemini-omni-1.1-flash`）

- Interactions API（`interactions.create`）経由の動画生成モデル。2026/8/27 GA。旧 preview 版（`gemini-omni-flash-preview`）は 2026/9/30 シャットダウンのため廃止モデルへ移動した。
- 長さは **3〜10 秒** で、これを制御する API パラメータは存在せず、長さ・BGM・効果音は**プロンプトで指示**する（モデルセレクタ下に `gemini.model.note.omniFlash` の注釈を表示）。
- パラメータはアスペクト比（16:9 / 9:16）と動画解像度（360p / 720p 既定 / 1080p / 4K）。1080p と 4K はアップスケールによる出力。長さセレクタは `supportedDurations` を宣言しないことで自動的に非表示となり、generation-store も対応モデル以外では `duration` をリクエスト・履歴に含めない。
- ネガティブプロンプトは API 非対応（`supportsNegativePrompt` 未宣言のため UI 非表示）。
- 参照画像は最大2枚（公式ドキュメントの例示上限。明示的な上限は未公表）。画像→動画生成（Image-to-Video）に対応。
- リクエストは同期型（LRO ポーリングなし）で、呼び出しが完了まで数分ブロックすることがある。経過時間表示はサービス内のローカルタイマー（5秒間隔）で `GENERATION_PROGRESS` イベントを発火して実現する。
- レスポンスの動画は inline（Base64、`output_video.data`）が既定。大きい動画で URI（`output_video.uri`）が返された場合は `x-goog-api-key` ヘッダー認証でダウンロードする。
- レスポンスメタデータとして interaction ID（`HistoryEntry.gemini.interactionId`。将来 `previous_interaction_id` による会話型編集に利用可能）とトークン使用量（`usageTokens`）を履歴エントリに記録する。
- 会話型動画編集（`previous_interaction_id`）・動画入力（Files API）は現時点では未対応（テキスト/画像→動画のみ）。

### 3.4 音楽生成

- Lyria モデル（Lyria 3 Clip / Lyria 3.5）による音楽生成に対応する。いずれも Interactions API 経路。
- **Lyria 3 Clip** (`lyria-3-clip-preview`): 30秒の短いクリップを生成。$0.04/曲。
- **Lyria 3.5** (`lyria-3.5`): 数分程度のフルレングス楽曲を生成。$0.08/曲。曲の長さ・構成はプロンプトで指定。2026/9/3 GA。Interactions API 経路（`interactions.create`、`response_format` 省略で MP3 出力）。レスポンスの `output_audio` から音声、`output_text` から歌詞・楽曲構成を取得し、interaction ID とトークン使用量を履歴に記録する。
- 旧 **Lyria 3 Pro** (`lyria-3-pro-preview`) は同価格で上位互換の Lyria 3.5 に置き換わったため廃止モデルへ移動した。
- Lyriaモデル選択時は画像・動画固有のUI（アスペクト比、解像度、生成枚数、長さ）がすべて非表示となる。
- プロンプトでジャンル、雰囲気、楽器、BPM、キー、歌詞（`[Verse]`, `[Chorus]`, `[Bridge]`セクションタグ）、タイムスタンプ指定が可能。歌詞に関する指示をプロンプトに含めることで、歌詞付き楽曲を生成できる。
- 参照画像を添付することで画像→音楽生成（Image-to-Music）が可能。公式上限どおり **10 枚**まで添付できる。

#### 参照画像の前処理（image / video / music 共通）

全ての生成経路で、APIに送る前に Electron `nativeImage` で以下の前処理を行う:

1. デコード
2. 長辺が **1920px** を超える場合のみ、縦横比を維持して縮小（`quality: 'best'`）
3. **JPEG (品質 85) に再エンコード**（PNG/WebP 入力も JPEG に統一）

枚数上限は各モデル定義の `maxReferenceImages` フィールドで宣言する（省略または 0 は画像入力非対応）。現状の値:

| モデル | maxReferenceImages |
| --- | --- |
| Nano Banana 2 / 2 Lite / Pro (gemini-3.1-flash-image / gemini-3.1-flash-lite-image / gemini-3-pro-image) | 14 |
| Veo 3.1 / Veo 3.1 Fast | 1（開始フレーム） / 3（被写体参照） |
| Veo 3.1 Lite | 1（開始フレームのみ） |
| Gemini Omni Flash (gemini-omni-1.1-flash) | 2 |
| Lyria 系 | 10 |
| Gemini TTS 系 | 未定義（画像入力非対応） |
| GPT Image 2.5 Flare / Sunburst | 16 |

Gemini 3 系の画像モデルはいずれも合計 14 枚が公式上限で、内訳のみモデルごとに異なる（Nano Banana 2 Lite はオブジェクト14枚、Nano Banana 2 はオブジェクト10枚＋キャラクター4枚、Nano Banana Pro はオブジェクト6枚＋キャラクター5枚＋スタイル参照3枚）。アプリ側は合計上限のみを宣言し、内訳の振り分けはモデルに委ねる。

動画 (Veo) の開始フレームモードは枚数 1 の単一スロットとして扱い、UI で新しい画像を添付すると **直前の画像を上書き**する。参照画像エリアには「開始フレーム」ラベルを表示してユーザに用途を明示する（被写体参照モードでは「被写体の参照画像（最大3枚・長さは8秒固定）」に切り替わる）。Gemini Omni Flash は最大2枚の通常マルチスロットとして扱う。

- ネガティブプロンプトは非対応。
- 生成された音楽は履歴ディレクトリに保存される。保存形式（拡張子）はAPIが返した`mimeType`に基づいて決まる（通常はMP3、44.1kHz ステレオ、SynthIDウォーターマーク付き）。
- APIレスポンスにテキストパート（歌詞、楽曲説明、BPM等のメタデータ）が含まれる場合、`audioTexts`フィールドにparts順序のまま配列として保存される。テキストパートの内容や数はAPIの挙動に依存し、構造的なラベル区分はない。
- 履歴パネルではサムネイルの代わりに音楽アイコンで表示される。
- クリックで音楽プレイヤーウィンドウ（モードレス）が開き、HTML5 `<audio>` 要素による再生コントロール付きで自動再生される。テキストパートがある場合はプレイヤーウィンドウ内にパートごとに区切り線付きで表示される。
- API は Lyria 3 Clip / Lyria 3.5 のいずれも `/v1beta/interactions` を使用し、`output_audio` / `output_text` から音声と歌詞を取得する。
- Single-turn only（マルチターン非対応）。

### 3.4.1 音声合成（TTS）

- Gemini TTS モデルによるテキスト読み上げ生成に対応する。いずれも Interactions API 経路。
- **Gemini 3.8 Flash-Lite TTS** (`gemini-3.8-flash-lite-tts`): 高スループット・低コスト向け。2026/9/22 GA。Interactions API 経路。音声 $0.009/分（2027/1/1 以降 $0.018/分）。無料枠あり。公式の課金単位はトークン（Input $0.50 / 1M tok、Audio Output $6.00 / 1M tok。2027/1/1 以降は $1.00 / $12.00）。
- **Gemini 3.8 Flash TTS** (`gemini-3.8-flash-tts`): 表現力・音質重視のフラグシップ。2026/9/22 GA。Interactions API 経路。音声 $0.0135/分（2027/1/1 以降 $0.027/分）。無料枠あり。公式の課金単位はトークン（Input $0.50 / 1M tok、Audio Output $9.00 / 1M tok。2027/1/1 以降は $1.00 / $18.00）。
- 旧 **Gemini 3.1 Flash TTS Preview** と **Gemini 2.5 Flash / Pro Preview TTS** はいずれも廃止モデルへ移動した。3.1 は ai.google.dev 上で 3.8 系を移行先とする非推奨扱いとなり、2.5 系は「過去に実際に利用したプロジェクトのみアクセス可」に制限され新規ユーザーは利用できない（`gemini-2.5-flash-preview-tts` は公式ガイドのサポートモデル表からも除外）。移行先は Gemini 3.8 Flash-Lite TTS / Flash TTS。
- 無料枠の RPM / TPM / RPD は Google が公開固定値を廃止し、プロジェクト単位で AI Studio の Rate Limits ダッシュボードに表示される方式に変更されている。本アプリでは無料枠キー使用時に「無料枠あり・実際の上限は AI Studio のレート制限ページで確認」という注釈（`gemini.model.freeTier.tts`）のみを表示し、固定の参考値は提示しない。
- TTSモデル選択時、ParameterPanelに以下を追加表示する:
  1. **スタイル**: 9種のプリセット + `カスタム`の選択肢を持つドロップダウン（表示形式 "スタイル名 : 効果"）。プリセット選択で下段のスタイル内容欄に該当する英語プロンプトが自動展開される。
  2. **スタイル内容**: 複数行テキスト入力。手動で編集するとスタイル選択は自動的に`カスタム`になる。
  3. **ボイス**: 30種の事前定義ボイスを "ボイス名 : 特徴" 形式で選択。
- プロンプト欄のラベルは「話させたい内容」に差し替わる。参照画像UIは非表示。
- Audio Tags 対応モデル（`gemini.supportsAudioTags`）では、プロンプト欄ラベル右に「Audio Tags の使い方」ボタンを表示。クリックで解説ダイアログを開く。ダイアログは Gemini 3.8 系の指示の分かれ方に合わせた2区分（「原稿内に書くタグ（発声・間）」と「スタイル欄で指定するもの（話速・トーン）」）で構成する。
- APIリクエスト:
  - エンドポイント: `/v1beta/interactions`
  - 入力は `[{type:'user_input', content:[{type:'text', text:<ユーザー入力>, annotations:[{type:'speech_metadata', style:<英語スタイル指示>}]}]}]`。3.8 系は本文を逐語トランスクリプトとして扱うため、スタイル指示は本文に混ぜず `speech_metadata` に載せる（スタイルが空なら `annotations` を省略）。
  - `generation_config.speech_config: [{voice: <ボイス名>}]`
  - `response_format: {type:'audio', mime_type:'audio/l16', sample_rate:24000}`。3.8 系の単発リクエストの既定出力は WAV だが、既存の PCM→MP3 変換をそのまま通すため raw PCM を明示要求する。
  - 応答は `output_audio` から取得し、interaction ID とトークン使用量を履歴に記録する。
- APIは raw PCM（例: `audio/L16;codec=pcm;rate=24000`）で返却される。後処理は次の順で行う:
  1. メモリ上で同梱ffmpegを介して MP3 に変換（CBR 160 kbps, 48 kHz, mono）。成功時は `.mp3` で保存。
  2. ffmpegが利用不可・失敗した場合は、純JSで RIFF/WAV ヘッダ（44バイト）を付与した WAV を `.wav` で保存。これによりAPIが成功している（=トークンが消費されている）にもかかわらず後処理失敗で結果が破棄されることを防ぐ。
- `HistoryEntry.styleInstruction` / `voice` にも保存され、履歴からの復元で元のスタイル/ボイスに戻る。
- 1リクエストあたりのテキスト長の上限は、現行の Gemini 3.8 系 TTS では公開されていない（旧 2.5 系では 4,000 バイトと明記されていた）。アプリ側でも文字数制限は設けていないため、長文は API のエラーで初めて判明する。

### 3.5 画像ビューア

- モードレスウィンドウとして開く（複数同時に開くことが可能）。
- 初期サイズは画像の等倍ピクセルサイズ。画面サイズの90%を超える場合は縮小して表示する。
- ウィンドウリサイズ時に画像は縦横比を維持して拡大・縮小する。

### 3.6 動画ビューア

- モードレスウィンドウとして開く。HTML5 `<video>` 要素による再生コントロール（再生/一時停止、シーク、音量）付き。
- 自動再生で開始される。

### 3.7 設定

- **言語**: i18nextによる日本語/英語切り替え。変更は即時反映。翻訳データは`src/renderer/i18n/locales/`に一元管理される。
- **テーマ**: ライト/ダーク/システム（OS追従）。変更は即時反映。
- **APIキー**: Electronの`safeStorage`で暗号化保存。マスク表示と表示/非表示トグル付き。以下の3種類のキーを最大7つ（デフォルト1・無料枠1・カスタム最大5）まで保持可能。
  - **デフォルトキー**: タイトルなし。通常利用想定。
  - **無料枠キー**: タイトルなし。このキーを選択中はモデルの料金ではなく無料利用枠の情報が表示される。
  - **カスタムキー**: タイトル付きで最大5つ追加可能。各キーに「無料枠キーとして扱う」フラグを設定できる。
  - キャプションバー（タイトルバー）の切替UIで、現在有効なキーを切り替える。アクティブキーが生成APIリクエストに使用される。
  - アクティブキーが無料枠種別の場合、ParameterPanelではモデル毎の参考価格は非表示となり、代わりに無料利用枠の情報（利用可否等）が表示される。両者は相反関係で同時表示されない。
- **履歴保存先**: ユーザーが任意のディレクトリを選択可能。変更時に既存履歴の移動有無を確認するダイアログを表示。

### 3.8 配布アーティファクト後処理 (Windows portable の zip 化)

- `electron-builder.yml` の `afterAllArtifactBuild` フックに `scripts/zip-portable.js` を指定し、Windows portable `.exe` をビルド完了後に `.zip` 圧縮する。未署名 `.exe` を直接配布するとブラウザやウイルス対策ソフトの警告が厳しいため、portable 版は zip 形式で配布する。
- フック内の処理:
  1. `context.platformToTargets` を走査し、Windows プラットフォーム上に `portable` ターゲットが含まれる場合のみ処理を行う (macOS / Linux ビルドでは何もせず通過する)。
  2. `context.artifactPaths` から `.exe` を抽出し、同 basename の `.exe.blockmap` が `artifactPaths` に含まれない `.exe` のみを portable 版として扱う。NSIS は `.exe` と `.exe.blockmap` を必ずペアで出力するため、`.blockmap` を伴わない `.exe` は確実に portable 版である。
  3. `archiver` (zlib level 9) で同名 `.zip` を生成し、成功後に元 `.exe` を削除する。
  4. 生成した zip パスの配列を戻り値として返す。electron-builder はこれを publish 対象アーティファクトに追加するため、`yarn release:win` 実行時には GitHub draft release に zip が含まれる。
- NSIS 関連アーティファクト (`.exe`, `.blockmap`, `latest.yml` など) は変更・削除しない。

## 4. データフロー

### 4.1 生成フロー

1. Renderer: ユーザーがパラメータを設定し、生成ボタンをクリック
2. Renderer -> Main (IPC): `generation:execute`でGenerationParamsを送信
3. Main: 履歴件数が上限を超えていないか検証
4. Main: API呼び出し
   - 画像: Interactions API `interactions.create`（生成枚数分ループ）
   - 動画 (Veo): Veo predictLongRunning → LROポーリング → 動画ダウンロード
   - 動画 (Omni): Interactions API `interactions.create`（同期）→ inline Base64 または URI ダウンロード
   - 音楽: Interactions API `interactions.create` → `output_audio` / `output_text`
   - 音声 (TTS): Interactions API `interactions.create` → `output_audio`（raw PCM）→ MP3 再エンコード
5. Main: 生成ファイルとメタデータを履歴ディレクトリに保存
6. Main: サムネイルを生成（画像: Electron nativeImage、動画: ffmpeg、音楽: サムネイルなし）
7. Main -> Renderer (IPC): HistoryEntryを返却
8. Renderer: 履歴一覧を再読み込み

### 4.2 API通信

- **Nano Bananaモデル**（例: gemini-3.1-flash-image）: Interactions API（`/v1beta/interactions`、SDK の `ai.interactions.create`）を使用。入力はコンテンツブロック配列（`{type: 'text', text}` のプロンプト + `{type: 'image', data, mime_type}` の参照画像）で、出力形式は `response_format: {type: 'image', aspect_ratio, image_size}` で指定する（`image_size` は `512` / `1K` / `2K` / `4K`。大文字の K が必須。アプリ内部の識別子 `512px` はサービス層で `512` に変換する）。`response_format` に画像を指定することで会話テキストの返却も抑制される。ネガティブプロンプトはテキストプロンプト内に埋め込み。1リクエストにつき1枚（`output_image`）なので、生成枚数分ループする。ループ内の1リクエストが失敗しても残りは継続し、全滅した場合のみ診断情報をまとめてエラーにする。Interactions API 経路（画像・音楽・音声・Omni 動画）では、レスポンスが inline Base64（`data`）ではなく URI（`uri`）で返された場合、`x-goog-api-key` ヘッダー認証でダウンロードしてメモリ上の Buffer にする（4K 画像や長尺音声は inline 上限を超えうる）。

#### URI 配信の保存経路（Veo のみ最終保存先へ直接書き込む）

- **Veo の URI 配信のみ、最終保存先へ直接ダウンロードする**。`history-service.reserveMediaPath('mp4')` で `<履歴>/images/<uuid>.mp4` を先に払い出し、SDK の `ai.files.download({ file, downloadPath })` でそこへ直接書き込む。これにより、一時ファイルへの書き込み → Buffer への読み戻し → 一時ファイル削除、という往復（書き込み2回・削除1回・全データのメモリコピー1回）がなくなる。
- 払い出した `id` はそのまま履歴エントリの ID になるため、ファイル名とエントリ ID が一致する。
- `createVideoHistoryEntry()` は `Buffer` と払い出し済みファイル（`ReservedMediaFile`）の両方を受け取れる。払い出し済みの場合は書き込みを省略し、`fileSize` は `fs.statSync()` から得る。サムネイルは元々ファイルパス起点（ffmpeg）なので変更なし。
- **失敗時のクリーンアップは必須**。払い出したファイルは metadata JSON が書かれて初めて履歴エントリになるため、それ以前に失敗すると「アプリからは見えないのにディスクを占有するファイル」が残る。`generateVideo()` 内の例外と、IPC ハンドラでの履歴エントリ作成失敗の両方で `discardReservedMedia()` を呼んで削除する。
- Interactions API 経路（Omni 含む）は既存どおり Buffer を返す。Omni は動作実績があるため意図的に変更していない。また Interactions 経路には元々一時ファイルの往復が無く、削減できるのはメモリコピー1回のみで、変更の見返りが小さい。
- **Veo 3.1モデル**（例: veo-3.1-generate-preview）: `/v1beta/models/{model}:predictLongRunning`エンドポイントを使用。開始フレームは `image`、被写体参照は `config.referenceImages`（最大3枚・`referenceType` は SDK の `VideoGenerationReferenceType.ASSET`（値は `ASSET`）・`durationSeconds` は 8 固定）で送る。レスポンスが URI 配信の場合は履歴ディレクトリ内の最終保存先へ直接ダウンロードする（後述）。レスポンスはLong-Running Operation（LRO）として返され、`/v1beta/{operationName}`を10秒間隔でポーリングする。完了時に動画のダウンロードURLを取得し、`x-goog-api-key`ヘッダーで認証してダウンロードする。ネイティブ音声生成を含む。ポーリングはタイムアウトなしで完了まで待機する（公式SDK準拠）。
- **Gemini Omni Flashモデル**（gemini-omni-1.1-flash）: Interactions API（`/v1beta/interactions`、SDK の `ai.interactions.create`）を使用。入力はコンテンツブロック配列（`{type: 'image', data, mime_type}` の参照画像 + `{type: 'text', text}` のプロンプト）、出力形式は `response_format: {type: 'video', aspect_ratio: '16:9' | '9:16', resolution: '360p' | '720p' | '1080p' | '4k'}` で指定する。リクエストは同期型で、レスポンスの `output_video` から動画（Base64 または URI）を取得する。`status !== 'completed'` または動画欠落時は `NO_VIDEO_GENERATED` エラーとして `status` / `output_text` を診断情報に載せる。
- **Lyriaモデル**（lyria-3-clip-preview / lyria-3.5）: Interactions API を使用。入力は参照画像ブロック + プロンプトのコンテンツブロック配列で、`response_format` は指定しない（既定の MP3 出力を使う）。音声は `output_audio` から取得する。テキストは `output_text` を使わず、`steps` の全 `model_output` ステップを走査して `text` ブロックを 1 ブロック = 1 要素で収集する（`collectInteractionTexts()`）。`output_text` は SDK 仕様で「最後の model_output の連結テキスト」であり、歌詞と楽曲構成 JSON のように複数ブロックがある場合に境界が失われ、前段ステップのテキストも脱落するため使えない。
- **Gemini 3.8 TTSモデル**（gemini-3.8-flash-tts / gemini-3.8-flash-lite-tts）: Interactions API を使用。入力は `user_input` ブロックで、スタイル指示は `speech_metadata` アノテーションに載せる。ボイスは `generation_config.speech_config`、出力形式は `response_format: {type:'audio', mime_type:'audio/l16', sample_rate:24000}` で指定し、`output_audio` の raw PCM を MP3 に再エンコードする。テキストは Lyria と同じく `collectInteractionTexts()` で全ブロックを収集する（TTS は音声のみの出力と公式に記載されているが、返った場合は破棄しない）。
- **SDK の型で検証する方針**: Interactions API の `response_format` は SDK のユニオン型に `{ [k: string]: any }` のキャッチオールが含まれるため、フィールド名を綴り間違えてもコンパイルが通り、API 側で黙って無視される。これを防ぐため、`gemini-service.ts` にローカルの狭い型（`ImageResponseFormat` / `AudioResponseFormat` / `VideoResponseFormat` / `InteractionContentBlock`）を定義し、リクエストオブジェクトはそちらで注釈する。Veo の `config` と参照画像は SDK が具体型（`GenerateVideosConfig` / `VideoGenerationReferenceImage`）を公開しているのでそれをそのまま使う。レスポンス型は SDK の戻り値型から導出する（ストリーミング分岐は `status` フィールドで除外）。
- **generateContent 経路は廃止した**。ai.google.dev の各生成ガイドは Veo を除くすべての生成メディアを Interactions API で記述する方針に変わっており、旧 `generateContent` 用の診断抽出（`finishReason` / `safetyRatings` / `promptFeedback`）も未使用になったため削除した。Interactions API が返す失敗情報は `status` と `output_text` のみで、候補単位の安全性内訳は取得できない（履歴 JSON の当該フィールドは過去エントリの互換用として型に残している）。
- 参照画像はリクエスト時にローカルファイルパスからBase64エンコードして送信
- APIキーはリクエスト時に暗号化ストレージから取得

## 5. セキュリティ

- APIキーはElectronの`safeStorage`により暗号化して保存される。
- RendererプロセスはAPIキーに直接アクセスせず、すべてのAPI操作はMainプロセス経由のIPC通信で処理される。
- コンテキスト分離とPreloadスクリプトにより、WebコンテンツとNode.js APIの間に安全な境界を確保する。

## 6. 拡張性

- モデル定義は`shared/constants.ts`に一元管理されている。新モデル追加時はこのファイルのみを更新する。
- 各モデル定義には対応パラメータが含まれ、UIの有効/無効制御が自動的に行われる。生成バックエンドのディスパッチは`mediaType`で行い、画像・音楽・音声はすべて Interactions API 経路で処理される。動画は`gemini.videoApi`フィールドで Veo（predictLongRunning、省略時）と Interactions API（`'interactions'`、Gemini Omni Flash）に分岐する。ネガティブプロンプトのAPI対応可否（`apiNegativePrompt`）もモデル定義で管理される。
- モデル定義のAPIプロバイダフィールドにより、将来的な複数プロバイダ対応に備えている。
- APIキーストレージはプロバイダ別にキー管理されており、複数APIキーに対応可能。

### 6.1 廃止モデルの扱い

提供元がシャットダウンしたモデルは、生成用の `MODEL_DEFINITIONS` から取り除き、`RETIRED_MODEL_DEFINITIONS` へ移動する。これにより新規生成では一切選択・実行できなくなる（生成モデル選択UI・プロバイダディスパッチは `MODEL_DEFINITIONS` のみを参照する）。一方で、過去にそのモデルで生成した履歴は引き続き完全に利用可能とする:

- 履歴フィルターのモデル一覧は `ALL_MODEL_DEFINITIONS`（= `MODEL_DEFINITIONS` + `RETIRED_MODEL_DEFINITIONS`）をマージし、実際に履歴に存在するモデルIDに絞り込んで構築する。廃止モデルの履歴が存在する場合のみフィルター候補に現れる。
- 履歴エントリのモデル名表示は保存済みの `modelDisplayName` を用いるため、定義の有無に依存しない。
- 廃止モデルの履歴からパラメータを復元する際は、`RETIRED_MODEL_DEFINITIONS[].replacementModelId`（移行先モデルID）に置換したうえで、移行先モデルの対応パラメータ（アスペクト比・解像度・品質・枚数・参照画像数など）にクランプする。これによりプロンプト・フィルター等は引き継ぎつつ、モデルとしては必ず移行先が選択される。移行先自体が後に廃止された場合も `resolveRestoreModelId()` が置換を再帰的にたどるため、必ず選択可能なモデルに着地する（ホップ数は定義数で上限を設け、循環参照でも停止する）。
- なお「シャットダウン日が未発表でも、提供元が上位互換モデルを出して旧モデルを実質的に新規利用不可としたもの」も廃止モデルとして扱う（例: Gemini 2.5 系 TTS）。判断根拠はモデル定義のコメントに残す。
- 現在の廃止モデル:
  - Imagen 4 ファミリ（`imagen-4.0-fast-generate-001` / `imagen-4.0-generate-001` / `imagen-4.0-ultra-generate-001`）。いずれも 2026/8/17 にシャットダウン。移行先は Nano Banana 2（`gemini-3.1-flash-image`）。
  - Nano Banana 2 / Pro の preview 版（`gemini-3.1-flash-image-preview` / `gemini-3-pro-image-preview`）。GA 版（`gemini-3.1-flash-image` / `gemini-3-pro-image`）のリリース（2026/5/28）に伴い、preview 版は 2026/6/25 にシャットダウン。移行先はそれぞれの GA 版。
  - Nano Banana（`gemini-2.5-flash-image`）。2026/10/2 にシャットダウン。移行先は Nano Banana 2（`gemini-3.1-flash-image`）。シャットダウンまで日が浅く、リリース後すぐに応答しなくなるため、シャットダウン前に選択肢から外した。
  - Gemini Omni Flash の preview 版（`gemini-omni-flash-preview`）。GA 版（`gemini-omni-1.1-flash`、2026/8/27）のリリースに伴い 2026/9/30 にシャットダウン。移行先は GA 版。
  - Lyria 3 Pro（`lyria-3-pro-preview`）。同価格で上位の Lyria 3.5（2026/9/3 GA）に置き換わり、公式ドキュメントからも記載が削除された。移行先は `lyria-3.5`。
  - Gemini 3.1 Flash TTS Preview（`gemini-3.1-flash-tts-preview`）。ai.google.dev 上で 3.8 系（`gemini-3.8-flash-tts` / `gemini-3.8-flash-lite-tts`）を移行先とする非推奨扱いとなった。Flash-Lite が直接の後継で、料金も安い。

備考:

- Nano Banana 2 / Nano Banana Pro の正式な課金単位は image tokens（output 1M トークン単位、$60 / $120 ）+ text tokens（input $0.50 / $2.00、output $3 / $12）の組合せだが、UI上は分かりやすさを優先して1枚あたり概算を表示する。
- Preview ステータスのモデルは料金が予告なく変更される可能性がある。
- **参考コストはトークン単位で表示しない**。トークン数は利用者が見積もれないため、`costLabel` には利用者が判断できる単位（1枚あたり / 1秒あたり / 1分あたり / 1曲あたり）に換算した値のみを載せる。公式の課金単位と換算式はこのドキュメントとモデル定義のコメントに記録する。
- TTS の分単価は、提供元が示す換算係数「音声1秒 = 25 トークン」（= 1分 1,500 トークン）を用いて算出している。Audio Output $6.00 / 1M tok → $0.009/分、$9.00 / 1M tok → $0.0135/分。テキスト入力（$0.50 / 1M text tok）は、1分の読み上げ原稿を多めに 500 トークンと見ても $0.00025/分にとどまり四捨五入すると消える額なので、`costLabel` には載せない。
- Gemini 3.8 系 TTS の料金は 2026/12/31 までの導入価格で、2027/1/1 に倍額となることが公表されている。`costLabel` の 2 行目に `2027/1/1~ $0.018/min` のように「適用開始日 + 単価」で記載する。説明文を足したり、モデル専用の翻訳キーを新設したりはしない。なお `costLabel` は i18n を経由しない共有定数なので、値は言語非依存（英数字と記号のみ）で記述する。提供元自身が概算としている値にだけ `~` を前置し（例: Gemini Omni Flash の `720p: ~$0.10/sec`）、それ以外の行には概算記号を付けない。
- GPT Image 2.5（Flare / Sunburst）は OpenAI が新規実装に推奨する現行世代であり、本アプリの OpenAI 側はこの2モデルのみを提供する。`xhigh` / `max` の品質段階と透過背景（PNG / WebP）に対応する。Flare と Sunburst は**1枚単価が同額**で、用途（Flare = 日常の高速生成、Sunburst = 編集精度重視）だけが異なる。公式カリキュレータのモデル選択肢が `GPT Image 2.5 (Sunburst and Flare)` の1つにまとめられており、品質係数テーブルも `gpt-image-2.5` の1本しかないため。
- **1枚単価の算出方法**: OpenAI は 2.5 系について静的な価格表を公開しておらず、ドキュメント上は対話型カリキュレータのみである。本アプリの `costLabel` は、そのカリキュレータが使用している公式のトークン算出式をそのまま用いて1枚単価に換算している。長辺の係数（Low 16 / Med 24 / High 48 / XHigh 64 / Max 96。旧 gpt-image-2 は Low 16 / Med 48 / High 96）からパッチグリッドを作り、`ceil(グリッド面積 × (2,000,000 + 画素数) ÷ 4,000,000)` トークン、これに画像出力単価 $30 / 1M tok を掛ける。この式は公式ドキュメントに価格表がある3サイズの掲載値を完全に再現するため、算出値の確度は公式掲載値と同等である。したがってアプリ上でも公式表と同じく小数第3位に丸めた値をそのまま表示し、概算記号は付けない。
- 料金は画素数に比例しない（式の `(2M + 画素数) / 4M` の項により逓減する）。そのため **横長4K（3840x2160）は2Kスクエア（2048x2048）より安い**。公式ドキュメントにも同旨の注記がある。
